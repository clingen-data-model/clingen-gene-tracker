# Catch-up scheduling for CronJob-triggered schedule:run

## Problem

In OpenShift, `php artisan schedule:run` is triggered by a CronJob a few times an hour
instead of by an always-on scheduler pod. If the Job starts after the minute an event's
cron expression matches, Laravel's `Schedule::dueEvents()` drops that run.

## Approach

Swap in a `Schedule` subclass (`App\Console\Scheduling\CatchUpSchedule`) by overriding
`Kernel::resolveConsoleSchedule()`. Only `dueEvents()` changes; `schedule:run` keeps its
filter, pause, overlap, hook, and output handling.

An event is due when:

- maintenance-mode and environment checks pass (same as `Event::isDue()`), and
- its most recent cron occurrence (in the event's timezone) is within the last
  `app.schedule_catch_up_minutes` minutes (env `SCHEDULE_CATCH_UP_MINUTES`, default 60), and
- an atomic `Cache::add()` claim on `schedule-occurrence:{mutexName}:{timestamp}` succeeds.

Consequences:

- Missed occurrences collapse to one run (only the latest occurrence is considered).
- Overlapping `schedule:run` invocations cannot both run an occurrence.
- A window of 0 reproduces stock "current minute only" behavior.
- Claims are consumed before `filtersPass()` / overlap checks, matching how a skipped minute
  behaves today.
- Claims require a shared cache store (redis), not `file`.
- On first deploy, an occurrence inside the window that the old scheduler already ran may
  run again; deploy just after a CronJob tick or temporarily set the window to 0.

## Test

`tests/Unit/Console/CatchUpScheduleTest.php` drives `dueEvents()` with `Carbon::setTestNow()`
to cover late-within-window, outside-window, collapse, zero window, timezone, environment,
and Kernel binding. It also guards against framework changes to `dueEvents()` /
`resolveConsoleSchedule()`.
